# Правила проекта Mouse Lab

## Рабочий язык

Отвечай пользователю на русском языке.

Имена файлов, классов, функций, команд, путей и commit message можно оставлять на английском, если они уже используются в проекте.

## Контекст проекта

Mouse Lab — десктопная игра на C++17 и raylib.

Проект собирается через CMake + Ninja.

Основной исполняемый файл:

```text
build/mouse_front.exe
```

Текущая архитектура проекта:

- одно окно raylib;
- `main.cpp` содержит основной цикл игры;
- `GameApp` управляет экранами;
- экраны переключаются через `ScreenType`;
- основные экраны:
  - `MainMenuScreen`
  - `ProfileSetupScreen`
  - `IntroScreen`
  - `LaboratoryHubScreen`
  - `MazeRunScreen`
- логика лабиринта находится в:
  - `Game`
  - `Maze`
  - `Mouse`
- общий контекст хранится в `AppContext`;
- профиль игрока хранится в `PlayerProfile`.

## Главный принцип работы

Работай маленькими безопасными шагами.

Одна задача — одно небольшое изменение.

Не делай большой архитектурный рефакторинг без явного запроса пользователя.

Не смешивай в одной правке:

- новую фичу;
- рефакторинг;
- косметику;
- переименование файлов;
- изменение архитектуры;
- исправление несвязанных багов.

Если задача выглядит большой, сначала предложи минимальный безопасный план.

.kilo/worktrees/solid-moss

## Правила перед изменением кода

Когда пользователь просит что-либо написать, реализовать, изменить, оформить или сгенерировать, сначала проверь, достаточно ли информации для качественного результата.

Не начинай сразу писать код, текст или большой фрагмент файла, если есть неоднозначность.

Перед выполнением задачи задай уточняющие вопросы, если неясно хотя бы одно из следующего:

- что именно должно получиться;
- где именно это должно находиться;
- какие файлы можно менять;
- какие файлы нельзя менять;
- какое поведение ожидается;
- какой внешний вид ожидается;
- какие ограничения важны;
- нужно ли сохранить старую логику;
- нужно ли делать минимальную правку или полноценный refactor;
- нужно ли писать готовый код или сначала только план.

Формат уточнения:

```text
Уточню ТЗ перед изменениями:

1. ...
2. ...
3. ...
```

Задавай по одному вопросу.

Сначала задавай самые важные вопросы, без которых легко сделать неправильную реализацию.

Не задавай лишние вопросы, если задача очевидная и маленькая.

Примеры маленьких задач, где можно не устраивать долгий опрос:

- исправить опечатку;
- поправить одну координату;
- заменить текст кнопки;
- добавить один include;
- исправить конкретную ошибку компиляции.

Если задача средняя или большая, обязательно сначала уточни ТЗ.

Примеры задач, где нужно уточнять ТЗ:

- “сделай нормальный экран”;
- “добавь окно”;
- “напиши систему уровней”;
- “сделай красиво”;
- “добавь русский текст”;
- “подключи ассеты”;
- “отрефактори архитектуру”;
- “напиши новый экран”;
- “сделай меню настроек”.

После ответов пользователя кратко зафиксируй итоговое ТЗ:

```text
Итоговое ТЗ:
- ...
- ...
- ...

Буду менять:
- ...
```

Только после этого приступай к написанию кода или текста.

Если пользователь явно пишет “без вопросов”, “сделай на своё усмотрение” или “просто дай вариант”, можно не задавать уточняющие вопросы, но нужно явно перечислить принятые допущения:

```text
Принятые допущения:
- ...
- ...
```

После этого можно выполнять задачу.

Если задача затрагивает больше 5 файлов или меняет архитектуру, сначала спроси подтверждение.

## Правила во время изменения кода

Меняй только те файлы, которые нужны для текущей задачи.

Не переименовывай классы, методы и файлы без необходимости.

Не меняй поведение игры, если задача этого не требует.

Не удаляй существующий рабочий код без объяснения причины.

Не добавляй новые абстракции, если можно решить задачу простым и понятным способом.

## Правила после изменения кода

После изменения кода напиши:

```text
Изменённые файлы:
- ...

Что изменено:
- ...

Риски:
- ...
```

Затем проверь сборку или предложи команду:

```powershell
cmake --build build
```

Если сборка упала, исправляй только ошибки сборки.

Не добавляй новый рефакторинг во время исправления ошибок сборки.

## Стиль кода

Используй C++17.

Предпочитай простой и понятный C++.

Сохраняй стиль имён проекта:

- классы: `PascalCase`;
- методы: `PascalCase`;
- локальные переменные: `camelCase`;
- значения enum: `PascalCase`.


Используй `static_cast<int>` при явном переводе `float`-координат в `int` для функций raylib.

Пример:

```cpp
DrawText(
    text,
    static_cast<int>(x),
    static_cast<int>(y),
    fontSize,
    RAYWHITE
);
```

## MazeRunScreen

`MazeRunScreen` должен быть полноценным экраном забега.

Он отвечает за:

- фон;
- header;
- panel под лабиринт;
- footer;
- кнопку возврата в `LaboratoryHub`;
- расчёт позиции лабиринта.

`Game` не должен сам решать, где на экране находится лабиринт.

Правильная схема:

```text
MazeRunScreen
-> считает Rectangle panel
-> считает Vector2 origin
-> вызывает game.Draw(origin)
```

`MazeRunScreen` может содержать методы:

```cpp
Rectangle GetMazePanelRect() const;
Vector2 GetGameOrigin() const;

Rectangle GetLabHubButtonRect() const;
bool IsLabHubButtonClicked() const;

void DrawHeader() const;
void DrawMazePanel() const;
void DrawFooter() const;
```

## Game и Maze

`Game`, `Maze` и `Mouse` должны работать как игровые компоненты внутри `MazeRunScreen`.

Если лабиринт рисуется внутри панели, используй `origin`.

`Game::Draw` должен принимать:

```cpp
void Draw(Vector2 origin) const;
```

`Maze::Draw` должен принимать:

```cpp
void Draw(Vector2 origin) const;
```

Мышь, HUD, modal и reset-кнопка должны учитывать этот же `origin`.

Не оставляй координаты лабиринта жёстко привязанными к `(0, 0)`.

Плохой вариант:

```cpp
DrawRectangle(
    cell.col * tileSize + padding,
    cell.row * tileSize + padding,
    tileSize - 2 * padding,
    tileSize - 2 * padding,
    RED
);
```

Хороший вариант:

```cpp
DrawRectangle(
    static_cast<int>(origin.x + cell.col * tileSize + padding),
    static_cast<int>(origin.y + cell.row * tileSize + padding),
    tileSize - 2 * padding,
    tileSize - 2 * padding,
    RED
);
```

## Логика движения мыши

Не меняй механику движения без отдельного запроса.

Сейчас движение мыши:

- выполняется стрелками;
- один шаг на одно нажатие;
- стены блокируют движение;
- при достижении цели уровень считается завершённым;
- счётчик `MOVES` увеличивается при успешном перемещении.

Не добавляй удержание клавиши, плавное движение, анимацию или новые действия без отдельной задачи.

## Русский текст

Финальная игра будет использовать русский текст.

Пока не переводи весь интерфейс на русский без отдельной задачи.

Когда будет задача на русский текст:

- исходники должны быть в UTF-8;
- нужно подключить шрифт с кириллицей;
- использовать `DrawTextEx`;
- не полагаться на default font raylib для кириллицы.

Пример будущего подхода:

```cpp
Font font = LoadFontEx("assets/fonts/pixel_cyrillic.ttf", 32, nullptr, 0);

DrawTextEx(
    font,
    "Добро пожаловать в лабораторию",
    Vector2{40.0f, 420.0f},
    24.0f,
    2.0f,
    RAYWHITE
);
```

## Ассеты

Пока не добавляй настоящую систему ассетов без отдельного запроса.

В будущем проекту понадобятся:

- пиксельные фоны;
- персонажи;
- аватары;
- мышь;
- UI-панели;
- шрифт с кириллицей;
- возможно, звуки.

Сейчас для экранов можно использовать raylib primitives:

- `DrawRectangle`;
- `DrawRectangleRec`;
- `DrawRectangleLinesEx`;
- `DrawText`;
- `DrawTextEx`, когда будет подключён шрифт.

## Документация состояния проекта

В проекте должен поддерживаться файл документации:

```text
docs/DOCUMENTATION.md
```

Этот файл описывает актуальное состояние проекта: реализованные экраны, игровой поток, механику, архитектурные решения и ближайшие технические задачи.

Если изменение кода влияет на поведение игры, структуру экранов, архитектуру, сборку, gameplay, ассеты, русский текст или пользовательский интерфейс, обнови `docs/PROJECT_STATE.md` в рамках той же задачи.

Не обновляй документацию при совсем мелких изменениях, которые не меняют функциональность:

- исправление опечатки;
- исправление отступов;
- изменение комментария;
- косметическая правка без изменения поведения.

Перед обновлением документации сначала прочитай текущий `docs/PROJECT_STATE.md`, если он существует.

В документации разделяй:

- что уже реализовано;
- что находится в работе;
- что запланировано на будущее;
- какие есть технические ограничения.

Не записывай планы как уже реализованный функционал.

Если функция только планируется, помещай её в раздел “Планируется” или “Открытые задачи”.

После изменения кода в ответе укажи, обновлялась ли документация:

```text
Документация:
- docs/PROJECT_STATE.md обновлён
```

или:

```text
Документация:
- не обновлялась, потому что функциональность не изменилась
```

Для кода предпочитай:
